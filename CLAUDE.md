# Agent Builder — Developer Context

This is a visual AI agent workflow builder. Users wire agent nodes, tool nodes,
and edges on a ReactFlow canvas, then run workflows against a FastAPI + DSPy backend.

> **For the full architecture document, see [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md)**.
> This file tells you *where things are* and *how to make changes*.

---

## ⚠️ Development Must Follow TDD (Test-Driven Development)

**This project uses Test-Driven Development exclusively.**
- Write tests FIRST, then implement the feature.
- All new code must have corresponding tests before being accepted.
- Running `uv run pytest -v` (backend) or `npx vitest run` (frontend) should pass
  at every step of development.
- E2E tests also exist: `npm run test:e2e` from `frontend/`.

## Data Flow: User Sends a Message

```
1. User types message in ChatOverlay input
2. ChatOverlay creates/open WebSocket → /ws/conversations/{id}/run
3. Sends {"prompt": "..."} (+ target_agent_id for per-agent execution)
4. Backend routes/execute.py:
   a. Accepts WebSocket, gets prompt
   b. Loads Canvas from DB (with all nodes + edges)
   c. Creates CanvasRunner(canvas, conversation_repo, conversation_id)
   d. Calls runner.run(prompt, send_event, target_agent_id)
5. CanvasRunner.run():
   a. setup(): compile tools → build worker agents
   b. Load conversation history from DB
   c. Build dspy.History if enabling conversation history
   d. Determine agent type (worker/router) and execute:
      - If target_agent_id is router: build router agent → forward → process
      - If target_agent_id is worker: attach events → run worker
      - If no target: chain workers via handoff edges
   e. Each agent runs StreamingReAct.aforward():
      - Iterates ReAct loop (max 10): thought → tool → observation → loop
      - Emits events: thought → tool_start → tool_result → thought → ... → finish
      - Final: extract answer from trajectory
   f. Auto-store memory for primary agent
   g. Send run_complete event
6. All events sent over WebSocket in real-time
7. Frontend ChatOverlay receives events and updates UI:
   - Steps shown live during streaming
   - Final answer displayed as assistant message
   - Canvas nodes glow green on node_id match
```

## Change Recipes

### Adding a New Field to AgentNode

**Backend:**
1. Add column in `models/canvas.py` (e.g., `temperature: Mapped[float]`)
2. Run `uv run alembic revision --autogenerate -m "add temperature to agent_nodes"`
3. Add field to `AgentNodeInput` / `AgentNodeResponse` in `models/api.py`
4. Include in `save_nodes_and_edges()` in `repos/canvas_repo.py`

**Frontend:**
1. Add field to `AgentNodeData` in `types/index.ts`
2. Add field to `CanvasSavePayload` agents mapping in `types/index.ts`
3. Add UI control in `AgentEditor.tsx`
4. Include in serialization in `useCanvasPersistence.ts` and `SidebarRail.tsx`
5. Display on node in `AgentNode.tsx`

**TDD:** Write tests for each layer before implementing.

---

### Adding a New Node Type

**Backend:**
1. Define ORM model in `models/canvas.py`
2. Run migration
3. Add Pydantic schemas in `models/api.py`
4. Add save/load logic in `repos/canvas_repo.py`
5. Handle in `CanvasRunner` if relevant to execution

**Frontend:**
1. Add data type in `types/index.ts`
2. Create node component in `components/canvas/` (must implement ReactFlow node interface)
3. Register in `CanvasView.tsx`'s `nodeTypes` object
4. Handle in `useCanvasPersistence.ts` serialization
5. Handle in `SidebarRail.tsx` export/import

**TDD:** Tests for each layer before implementation.

---

### Adding a New Execution Event Type

**Backend:**
1. Emit the new event in `runner.py` or `streaming_react.py`
2. Follow the wire protocol: `{"type": "new_type", ...}`

**Frontend:**
1. Add to `ExecutionEvent` union in `types/index.ts`
2. Handle in `ChatOverlay.tsx`'s `onmessage` handler
3. Add rendering in the turn/step display

---

### Adding a New API Endpoint

**Backend:**
1. Define request/response Pydantic models in `models/api.py`
2. Implement business logic in the appropriate repo
3. Add route in `routes/canvas.py` (or new router)
4. Register router in `main.py`

**Frontend:**
1. Add fetch wrapper in `lib/api.ts`
2. Call it from component or hook
3. Update zustand store if needed

## Key Architecture Decisions

1. **DSPy over beeai** — The project migrated from beeai-framework to DSPy.
   StreamingReAct is a custom subclass that emits per-iteration events.

2. **Deferred router build** — Router agents are NOT built during `setup()`.
   They're built lazily via `_build_router_agent()` when first invoked by a
   handoff tool or by `run()` directly. This is because routers need `send_event`
   and `history` which aren't available during setup.

3. **Shared mem0 Memory** — A single `mem0.Memory` instance is shared across all
   agents to avoid local-qdrant file-locking issues. Isolation is achieved via
   `user_id`.

4. **Conversation status stays "active"** — After each `run()`, the conversation
   status is NOT set to "completed". This enables multi-turn conversation history
   across WebSocket connections.

5. **SQLite for tests** — Backend tests use `sqlite+aiosqlite:///test.db` instead
   of PostgreSQL. The test DB is dropped and recreated per test via `fresh_db`.

6. **Client-generated IDs** — UUIDs for nodes and edges are generated on the
   frontend and persisted. The backend preserves them across saves (except import,
   which remaps to avoid collisions).

7. **No FK on edge references** — `edges.source_node_id` and `target_node_id` are
   plain UUIDs without foreign key constraints because they can reference either
   `agent_nodes` or `tool_nodes`.

8. **Deno/Pyodide sandbox for tool execution** — All tool code (both agent runs
   and interactive testing) executes in a Deno subprocess running Pyodide (WASM
   Python) via DSPy's `PythonInterpreter`. Host-side `exec()` is used only for
   extracting function metadata (`__name__`, `__doc__`, `__annotations__`) that
   DSPy needs to build tool descriptors — never for execution. The sandbox has
   no access to host filesystem, network, or env vars by default. See
   [ADR-0002](./docs/adr/0002-deno-sandbox-tool-execution.md).

9. **Sandbox singleton** — The Deno/Pyodide process is expensive to start (~2s).
   It's pre-warmed during FastAPI lifespan startup and kept alive across requests.
   Managed by `canvas_server.sandbox.Sandbox`.

10. **`@requires_deno` test marker** — Sandbox integration tests skip gracefully
    in CI environments without Deno installed (`pytest.mark.skipif(not shutil.which("deno"))`).
    Unit tests (inspect, coerce) don't need Deno.

11. **In-Memory RAG for Workers** — RAG documents are stored as standard relational rows in PostgreSQL. Chunks are computed using a paragraph-aligned splitter and embedded dynamically in-memory at run-time using DSPy embedders. This avoids vector synchronization bugs during canvas auto-saves, which are supported by delta upserting nodes instead of destroying/recreating them.
