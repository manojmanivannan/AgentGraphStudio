# MCP Client Integration Patterns in Mainstream Agent Frameworks

**Research ticket:** [#117](https://github.com/manojmanivannan/AgentGraphStudio/issues/117)
**Date:** 2026-10-10
**Scope:** How LangChain/LangGraph, OpenAI Agents SDK, Claude Agent SDK, LlamaIndex, and Pydantic AI integrate tools from *remote* MCP servers (Streamable HTTP transport) into their agent loops.

All claims are sourced from official documentation and framework source code (primary sources), read on 2026-10-10. Version caveats are flagged inline where the API surface is in transition.

---

## TL;DR

| Question | What mainstream frameworks actually do |
|---|---|
| Tool surfacing | **Fetch per run, convert lazily.** No framework registers tools via a hidden connect-time hook the user never sees; MCP `tools/list` is fetched either once when the user asks for tools (LangChain, LlamaIndex) or at every agent run step (OpenAI Agents SDK, Pydantic AI). MCP JSON `inputSchema` is passed through essentially verbatim (LangChain, OpenAI, Pydantic AI) or re-hydrated into a dynamic Pydantic model (LlamaIndex). |
| Name collisions | **Three different strategies:** hard error (OpenAI Agents SDK, Pydantic AI → opt-in `include_server_in_tool_names` / `tool_prefix`), automatic namespace prefixing (Claude Agent SDK `mcp__<server>__<tool>`, LangChain's new `MCPAdapter` `{server}_{tool}`), and **last-write-wins silently** (LlamaIndex). The MCP spec defines tool-name uniqueness only per-server ([spec §Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)), so cross-server disambiguation is entirely a client convention. |
| Connection lifetime | **Async-only everywhere; long-lived session preferred over per-call reconnect.** LlamaIndex is the outlier doing connect/init/teardown **per tool call**; OpenAI Agents SDK and Pydantic AI use a long-lived session owned by an explicit or ref-counted context manager; Claude Agent SDK spawns the harness per `query()` run but with reconnect+cache support. |
| Tool-list refresh | **Mostly manual.** Only Pydantic AI (fully) and Claude Agent SDK honor `notifications/tools/list_changed` from `listChanged`-capability servers. OpenAI Agents SDK caches only behind `cache_tools_list=True` with a manual `invalidate_tools_cache()`. LangChain/LlamaIndex never cache but also never refresh — the list is stale the moment you fetch it. |
| Output guardrails | **Only Claude Agent SDK ships real guardrails** (10k-token warning / 25k-token cap, 50k-char overflow-to-disk, 16 MB transport cap, middle-truncated errors). OpenAI Agents SDK, Pydantic AI, LlamaIndex, and langchain-mcp-adapters pass MCP tool output to the model **verbatim with no truncation, size cap, or injection labeling**. The MCP spec says clients "SHOULD validate tool results before passing to LLM" — almost nobody implements this. |

---

## Cross-cutting: what the MCP spec fixes vs. leaves open

The [2025-06-18 spec, §Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) sets the ground rules every client builds on:

- A tool's `name` is the "Unique identifier for the tool" — uniqueness is meaningful only **per server**; the spec imposes no cross-server convention. This is why every multi-server client needs its own collision policy.
- Servers declare a `tools` capability with `listChanged: true` and `SHOULD` send `notifications/tools/list_changed` when the list changes. How a client reacts is undefined — the notification is only an invitation to re-fetch.
- Tool results carry `content` (text/image/audio/resource_link/embedded resource) plus optional `structuredContent`, and two error channels (JSON-RPC protocol errors vs. in-band `isError: true`). `structuredContent` is "server-produced result data"; for compat, a tool SHOULD also return the serialized JSON as a text block.
- Trust posture: tool **annotations** "MUST be considered untrusted unless they come from trusted servers"; clients "SHOULD validate tool results before passing to LLM"; the spec's warning insists on human-in-the-loop with the ability to deny tool invocations.

The spec defines the wire; everything below — schema adaptation, naming, lifetimes, caching, sanitization — is client-side convention that varies sharply between frameworks.

## 1. LangChain / LangGraph (`langchain-mcp-adapters` → `langchain[mcp]`)

> **Moving target:** the standalone [`langchain-ai/langchain-mcp-adapters`](https://github.com/langchain-ai/langchain-mcp-adapters) README (v0.3.2 at time of reading) states the package is "**no longer actively maintained**" and migration to the `langchain.mcp` namespace via `langchain[mcp]>=1.4.0` (beta) is required. Findings cover both the adapter library (source read at `main`) and the successor `MCPAdapter`. Source: [README](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/README.md), [MCP docs](https://docs.langchain.com/oss/python/langchain/mcp).

### Tool surfacing

- **Explicit bulk load, then manual wiring.** `MultiServerMCPClient.get_tools()` / `load_mcp_tools()` call `session.list_tools()` per configured server (paginated via `_list_all_tools`, capped at 1000 pages) and convert every MCP `Tool` to a LangChain `StructuredTool`. The resulting list is passed straight into `create_agent(..., tools)` or a LangGraph `ToolNode` — the framework registers nothing on the model binding until you hand over the list. Source: [`tools.py`](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/langchain_mcp_adapters/tools.py), [`client.py`](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/langchain_mcp_adapters/client.py).
- **Schema mapping is a passthrough.** `convert_mcp_tool_to_langchain_tool()` builds a `StructuredTool` with `args_schema=tool.inputSchema` — the raw MCP JSON-Schema dict is used directly, no Pydantic model generation — with `name=tool.prefix`-aware name, `description=tool.description or ""`, and `response_format="content_and_artifact"`. MCP structured results are carried as `MCPToolArtifact(structured_content=...)` on `ToolMessage.artifact`, kept out of the model-visible text. Source: [`tools.py` (v0.3.2)](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/langchain_mcp_adapters/tools.py).
- **Name collisions: opt-in prefixing in the legacy adapter, automatic in the new one.** Legacy `MultiServerMCPClient(tool_name_prefix=True)` renames to `f"{server_name}_{tool.name}"`; with it off, tools from all servers are concatenated with **no collision error and no de-dup**. In the successor `MCPAdapter`/`ClientGroup`, prefixing is always-on for multi-server configs: tools are namespaced as `{server}_{tool}` ("two servers exposing the same tool name stay distinguishable"). Sources: [`client.py`](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/langchain_mcp_adapters/client.py), [connections docs](https://docs.langchain.com/oss/python/langchain/mcp/connections), [migration guide](https://docs.langchain.com/oss/python/migrate/langchain-mcp-adapters).

### Connection lifetime

- **A new session per tool call.** `get_tools()`'s docstring: "A new session will be created for each tool call." Each converted tool opens `async with create_session(...)`, `initialize()`, `call_tool`, and tears down per invocation — a fresh MCP handshake on every single tool call. No pooling. Source: [`client.py`, `tools.py`](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/langchain_mcp_adapters/tools.py).
- **`MultiServerMCPClient` is deliberately not a context manager** — `__aenter__`/`__aexit__` raise `NotImplementedError` ("As of langchain-mcp-adapters 0.1.0…"), and explicit per-server sessions come from an `@asynccontextmanager` `client.session(server_name)` (async-only; no sync client exists). Source: [`client.py`](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/langchain_mcp_adapters/client.py).
- **The successor `MCPAdapter` inverts this:** entering the context connects; the returned tools are "reentrant — each time a tool is invoked, it opens the client, runs the MCP call, and releases it," and holding the context open lets them reuse the live connection. Deployment guidance: "discover per run, but reuse its connections underneath," optionally sharing one `httpx` pool via `httpx_client_factory`. Source: [connections docs](https://docs.langchain.com/oss/python/langchain/mcp/connections).

### Tool-list caching / refresh

- **No caching, no `listChanged` handling in the legacy adapter.** Every call to `get_tools()` performs a full re-list; `callbacks.py` handles only logging/progress notifications — no `tool_list_changed` handler anywhere. Lists go stale between explicit re-calls. Source: [`callbacks.py`](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/langchain_mcp_adapters/callbacks.py).
- **Explicit cache modes in the new `MCPAdapter`** (FastMCP-backed): `list_tools(cache_mode="use" | "refresh" | "bypass")` — `use` honors the server's TTL-style cache hints, `refresh` force-refetches, `bypass` skips the cache entirely. Source: [connections docs](https://docs.langchain.com/oss/python/langchain/mcp/connections).

### Guardrails on untrusted output

- **None in the adapter itself.** Content blocks are converted verbatim — no length cap, no sanitization, no untrusted marking. Only error propagation exists: `isError=True` results become `ToolMessage(status="error")` with the server's content returned verbatim so the agent "can self-correct." Sources: [`tools.py`](https://raw.githubusercontent.com/langchain-ai/langchain-mcp-adapters/main/langchain_mcp_adapters/tools.py), [tools docs](https://docs.langchain.com/oss/python/langchain/mcp/tools).
- **Suggested protections are framework-adjacent, not MCP-specific:** reading MCP `annotations` (e.g. `destructiveHint`) from tool metadata to gate calls with `HumanInTheLoopMiddleware`/interrupt configs, elicitation-as-interrupt, and user-authored guardrail middleware. The `structuredContent` → artifact split (above) is the closest thing to a model-visible guardrail — raw structured data never reaches the model. Sources: [tools docs](https://docs.langchain.com/oss/python/langchain/mcp/tools), [guardrails docs](https://docs.langchain.com/oss/python/langchain/guardrails).

## 2. OpenAI Agents SDK (`openai-agents-python`)

All from the [official MCP docs](https://openai.github.io/openai-agents-python/mcp/) and source on `openai/openai-agents-python` `main` ([`src/agents/mcp/server.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/server.py), [`util.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/util.py), [`manager.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/manager.py)).

### Tool surfacing

- **Lazy per-run fetch, not connect-time registration.** `MCPServer.connect()` only opens the transport and initializes the `ClientSession`. Tools are fetched during each agent run: `Agent.get_all_tools()` → `MCPUtil.get_all_function_tools(...)` → `server.list_tools(...)` per server. Docs confirm: "Every agent run calls `list_tools()` on each MCP server." Source: [MCP docs](https://openai.github.io/openai-agents-python/mcp/).
- **Schema mapping is a near-passthrough with an OpenAI-compat patch.** `MCPUtil.to_function_tool()` copies MCP `inputSchema` directly; because "MCP spec doesn't require the inputSchema to have `properties`, but OpenAI spec does," it adds `schema["properties"] = {}` when missing. Opt-in strict-mode conversion via `mcp_config={'convert_schemas_to_strict': True}` falls back to the original schema if conversion fails. The resulting `FunctionTool` carries `_mcp_tool_binding = (server_log_name, raw_tool_name, server_index)` so the SDK still invokes the original MCP tool name upstream. Source: [`util.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/util.py).
- **Name collisions: hard error; opt-in namespaced prefixing.** `MCPUtil.get_all_function_tools` iterates servers in order and raises `UserError("Duplicate tool names found across MCP servers: ...")` on the first duplicate, suggesting `include_server_in_tool_names=True`, which yields `mcp_{server}__{tool}` names (ASCII-sanitized, over-length names get a sha1 suffix). With prefixing on, remaining collisions get deterministic hash disambiguation; names colliding with reserved local tool names are rejected. Source: [`util.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/util.py).
- Extra surfacing control worth noting: static allow/block `tool_filter` or a dynamic callable per `(run_context, agent, server_name)`; a filter error silently excludes the tool "for safety." Source: [`server.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/server.py).

### Connection lifetime

- **Long-lived session owned by explicit lifecycle calls or a context manager.** `connect()` puts the transport + `ClientSession` in an `AsyncExitStack`; "The server is expected to remain connected until `cleanup()` is called." `list_tools`/`call_tool` raise `UserError("Server not initialized…")` if called before `connect()`. `async with MCPServerStreamableHttp(...) as server:` maps to `__aenter__=connect()`, `__aexit__=cleanup()`; `terminate_on_close=True` sends HTTP `DELETE` on teardown. Sources: [MCP docs](https://openai.github.io/openai-agents-python/mcp/), [`server.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/server.py).
- **Session reused across runs, serialized, but not pooled across instances.** Streamable HTTP requires serialized requests, so `MCPServerStreamableHttp` routes all calls through an internal `_request_lock`. `MCPServerManager` wraps multiple servers as an async context manager with `active_servers`/`failed_servers` (`drop_failed_servers=True` by default), `reconnect(failed_only=True)`, per-call connect/cleanup timeouts (default 10 s per docs). No synchronous client API — async only. Sources: [`server.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/server.py), [`manager.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/manager.py).

### Tool-list caching / refresh

- **Opt-in cache, manual invalidation; `listChanged` is not handled.** `cache_tools_list: bool = False` — docstring: "If `True`, the tools list will be cached and only fetched from the server once… The cache can be invalidated by calling `invalidate_tools_cache()`." Otherwise the list is re-fetched on every `list_tools()` (which happens every agent run). There is **no handling of `notifications/tools/list_changed`** anywhere in the MCP modules. The docs recommend `cache_tools_list=True` "only if you are confident that the tool definitions do not change frequently." Sources: [MCP docs](https://openai.github.io/openai-agents-python/mcp/), [`server.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/server.py).
- Cache hygiene details: reads return deep copies (`model_copy(deep=True)`) so callers can't mutate cached schemas; paginated listing that hits a repeated cursor or page limit discards all accumulated tools rather than "exposing or caching partial results."

### Guardrails on untrusted output

- **No truncation, size caps, or injection labeling.** `MCPUtil.invoke_mcp_tool` maps result content essentially verbatim (text → `ToolOutputTextDict`, image → base64 data-URI, other → `model_dump_json()`); `structuredContent` (if present and used) is exclusively `json.dumps`ed to the model; error results keep the in-band `content` text "because that is where the actionable failure text lives." Results are additionally attached to tracing spans unless `trace_include_sensitive_data=False`. Source: [`util.py`](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/mcp/util.py).
- **Mitigation is opt-in, not automatic:** per-server `tool_input_guardrails` / `tool_output_guardrails`, `require_approval` (always/never, per-tool or callable), and tool filters. The docs' trust warning: "MCP tools can expose data from the model context and perform actions with the credentials you provide… Connect only to servers you trust, use least-privilege credentials… and require approval for sensitive operations." No prompt-injection-specific labeling exists. Source: [MCP docs](https://openai.github.io/openai-agents-python/mcp/).

## 3. Claude Agent SDK / Claude Code

From `code.claude.com` docs (the `docs.claude.com` URLs for [MCP](https://code.claude.com/docs/en/mcp) and the [Agent SDK MCP page](https://code.claude.com/docs/en/agent-sdk/mcp) 301-redirect here) and the [Python SDK reference](https://code.claude.com/docs/en/agent-sdk/python). The SDK drives the Claude Code binary as harness, so the CLI's CLI behavior and the SDK's behavior are one implementation.

### Tool surfacing

- **Auto-registration at connect time, with a mandated namespace.** Servers arrive via the `mcp_servers` SDK option (dict of `McpServerConfig | str | Path`), a project `.mcp.json`, or settings/plugins; remote servers are configured as `{"type": "http", "url": ..., "headers": ...}` (SSE is documented as deprecated in favor of HTTP). Tools are discovered at connect and appear in the session/init message's `tools` array — the docs state MCP tool names "start with `mcp__`", following "the naming pattern `mcp__<server-name>__<tool-name>`." Source: [Agent SDK MCP](https://code.claude.com/docs/en/agent-sdk/mcp).
- **Collisions resolved by namespace, not by merging.** Because the *server name* is the namespace, collisions surface as duplicate server names across config scopes; Claude Code matches duplicates by name with precedence managed > local > project > user > plugin, uses "the entire server entry from that source," and warns on same-name/different-endpoint conflicts. Reserved built-in server names are rejected. Source: [MCP docs](https://code.claude.com/docs/en/mcp).

### Connection lifetime

- **Per-`query()` run re-registers servers; a `ClaudeSDKClient` holds a managed session.** "Claude Code registers the servers you pass in `options.mcpServers` at startup and emits the `init` message once the first-turn wait, if any, resolves"; a first turn may wait up to `MCP_TIMEOUT` (30 s default) for servers to connect. Each new `query()` re-reads the config (fresh session). `ClaudeSDKClient` gives explicit lifecycle — `connect()`/`disconnect()`/`interrupt()`, usable as async context manager — plus mid-session controls (`get_mcp_status()`, `reconnect_mcp_server(server_name)`, `toggle_mcp_server(...)`). Source: [Agent SDK MCP](https://code.claude.com/docs/en/agent-sdk/mcp), [Python SDK reference](https://code.claude.com/docs/en/agent-sdk/python).
- **Built-in reconnect with exponential backoff, plus an optional discovery cache.** "Claude Code reconnects a remote server that drops mid-session and retries an HTTP or SSE server's first connection after a transient error" — "up to five attempts, starting at a one-second delay and doubling it each time." The opt-in discovery cache (`MCP_DISCOVERY_CACHE=1`) shows previously-seen remote servers as `cached 2h ago · connects on first use · 5 tools`, deferring an actual connect until the first tool call. Source: [MCP docs](https://code.claude.com/docs/en/mcp).

### Tool-list caching / refresh

- **This is the only framework that fully honors `list_changed`.** "An MCP server can change the tools, prompts, or resources it offers while connected and send a `list_changed` notification. When one arrives: In an interactive terminal session… Claude Code fetches the updated list… In non-interactive mode with the `-p` flag and in the Agent SDK, Claude Code refreshes only the tool list on these notifications." If a refresh fails, previously discovered tools are kept "until a later refresh succeeds." With the discovery cache, a fresh run can start from a prior session's tool list and reconcile on first connect. Sources: [MCP docs](https://code.claude.com/docs/en/mcp), [Agent SDK MCP](https://code.claude.com/docs/en/agent-sdk/mcp).

### Guardrails on untrusted output

- **The only framework with shipped, hard guardrails:**
  - Token cap: "Claude Code displays a warning when MCP tool output exceeds 10,000 tokens and limits output to 25,000 tokens by default" (`MAX_MCP_OUTPUT_TOKENS` to change; warning threshold fixed). Oversized successful text results are **saved to a file and replaced in the conversation with a message naming the file path** so the agent can read the output back in portions.
  - Additional caps: results >50,000 characters are filed to disk regardless of token count unless the tool declares `_meta["anthropic/maxResultSizeChars"]` (hard ceiling 500,000 chars); transport-side, Claude Code stops reading after any single decompressed HTTP body / SSE event passes **16 MB**; error results are middle-truncated (first 5k + last 5k chars) past ~11k chars.
  - Source: [MCP docs](https://code.claude.com/docs/en/mcp), [Agent SDK MCP](https://code.claude.com/docs/en/agent-sdk/mcp).
- **Injection handling is consent + permissions, not per-result labeling.** Docs: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk"; the security page adds that Anthropic "does not security-audit or manage any MCP server," and that committed `enableAllProjectMcpServers` settings are ignored in untrusted folders. "MCP tools require explicit permission before Claude can use them" via `allowedTools` patterns such as `"mcp__github__*"`; org-level control can `ask` on every call (even in `bypassPermissions`) or `blocked` ("Claude Code filters the tool out before Claude sees it"). There is **no documented per-result injection badge** — the mitigation strategy is explicit approval, permission rules, and output caps. Source: [MCP docs](https://code.claude.com/docs/en/mcp), [security docs](https://code.claude.com/docs/en/security).

## 4. LlamaIndex (`llama-index-tools-mcp`)

From the [official MCP example docs](https://developers.llamaindex.ai/python/examples/tools/mcp/) and source in `run-llama/llama_index` under `llama-index-integrations/tools/llama-index-tools-mcp` ([`base.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/tools/llama-index-tools-mcp/llama_index/tools/mcp/base.py), [`client.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/tools/llama-index-tools-mcp/llama_index/tools/mcp/client.py)).

*(Terminology correction vs. older write-ups: there is no `get_tools_and_async_tools` API anywhere in the repo — the real entry points are module-level `get_tools_from_mcp_url` / `aget_tools_from_mcp_url` and `McpToolSpec.to_tool_list` / `to_tool_list_async`.)*

### Tool surfacing

- **Eager bulk conversion into static `FunctionTool`s.** Calling `to_tool_list_async()` (or the module-level helpers) runs `list_tools()` once and converts each MCP tool via `create_model_from_json_schema(tool.input_schema, model_name=f"{tool.name}_Schema")` — MCP JSON Schema is **re-hydrated into a dynamic Pydantic model** — then `FunctionTool.from_defaults(async_fn=..., tool_metadata=...)`. The agent receives a plain list; the framework registers nothing beyond what you pass. Notably, the server-controlled `tool.description` is passed through **verbatim** into `ToolMetadata(description=tool.description)`. Source: [`base.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/tools/llama-index-tools-mcp/llama_index/tools/mcp/base.py).
- **JSON-Schema → Pydantic details** live in `tool_spec_mixins.py`: `$ref` resolution, `enum` → `Literal[...]`, `anyOf` → `Union[...]`, and a base-type mapping (`string→str`, `array→List`, etc.). `partial_params` / `global_partial_params` can pin argument defaults, which are then removed from the schema sent to the model. Source: [`tool_spec_mixins.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/tools/llama-index-tools-mcp/llama_index/tools/mcp/tool_spec_mixins.py).
- **Name collisions: silently last-write-wins.** `McpToolSpec` has no dedupe/rename logic; the agent layer builds `tools_by_name = {t.metadata.name: t for t in tools}`, so duplicate names across servers overwrite each other with **no error and no warning**. The only filter is an `allowed_tools` allowlist (an empty allowlist yields zero tools with a warning). Source: [`base.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/tools/llama-index-tools-mcp/llama_index/tools/mcp/base.py), [`multi_agent_workflow.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/agent/workflow/multi_agent_workflow.py).

### Connection lifetime

- **A fresh session per operation — the most per-call-oriented design.** `BasicMCPClient(subclasses the MCP SDK's `ClientSession`) wraps each operation (`call_tool`, `list_tools`, etc.) in `async with self._run_session() as session:` → `streamable_http_client(url=...)` + `ClientSession(read, write)` + `await session.initialize()`, then teardown on exit. Nothing is reused between calls except a shared `httpx.AsyncClient`. Confirmed unchanged at tag `v0.14.1`. Source: [`client.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/tools/llama-index-tools-mcp/llama_index/tools/mcp/client.py).
- **You can hold your own session.** A pre-connected `ClientSession` may be passed to the helpers ("You can also pass in a custom `ClientSession`"), but LlamaIndex itself never caches or pools MCP sessions; OAuth token storage defaults to in-memory only ("Not suitable for production use across restarts"). Sync support exists only as an auto-generated shim (`async_to_sync`) that raises if a loop is already running. Sources: [MCP example docs](https://developers.llamaindex.ai/python/examples/tools/mcp/), [`function_tool.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/function_tool.py).

### Tool-list caching / refresh

- **Fetched once, frozen, no refresh.** The `FunctionTool` list is static from the moment `to_tool_list[_async]` returns; nothing re-queries the server mid-run, and the only cache is of *resolved Pydantic schema models*, not the tool list. The docs page mentions no refresh mechanism. (A separate `llama-index-tools-mcp-discovery` package queries a discovery API for *server recommendations* — not a live tool-list refresh.) Source: [`base.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/tools/llama-index-tools-mcp/llama_index/tools/mcp/base.py), [MCP docs](https://developers.llamaindex.ai/python/examples/tools/mcp/).

### Guardrails on untrusted output

- **None — the weakest of the five.** `call_tool` returns the raw `CallToolResult`; the default output path is `TextBlock(text=str(raw_output))` — i.e., a `str()` of the whole Pydantic result object can reach the model verbatim, unbounded. No truncation, size cap, or injection labeling exists anywhere in this path; repo-wide searches for truncation limits and "injection" return nothing relevant. Existing mitigations are only (a) the `allowed_tools` allowlist, (b) a user-supplied output `callback` that can rewrite results, and (c) a transport-level `max_sse_event_size` buffer cap (a transport concern, not a model-input guardrail). Source: [`base.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/tools/llama-index-tools-mcp/llama_index/tools/mcp/base.py), [`function_tool.py`](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/function_tool.py), [MCP python-sdk `streamable_http.py`](https://github.com/modelcontextprotocol/python-sdk/blob/main/src/mcp/client/streamable_http.py).

## 5. Pydantic AI

> **Version note:** the documented-and-referenced `MCPServerStreamableHTTP` is the *legacy* API. In the current release line (v2.x) the `MCPServer*` hierarchy was removed in favor of `MCPToolset`, built on the FastMCP client; the base class carries a deprecation warning ("The concrete subclasses will be removed in v2") in the final v1 release. The [MCP docs page](https://pydantic.dev/docs/ai/mcp/overview/) (redirect target of the old `ai.pydantic.dev/mcp/`) now leads with `MCPToolset`. Findings cover both the v1 legacy class (v1.107.7) and current `MCPToolset` (main). Source: [`pydantic_ai/mcp.py` on main](https://github.com/pydantic/pydantic-ai/blob/main/pydantic_ai_slim/pydantic_ai/mcp.py), [v1.107.7](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/mcp.py).

### Tool surfacing

- **Lazy per-run-step fetch, not connect-time.** The Agent only stores toolsets at construction; no network I/O happens then. Each model-request step calls `ToolManager.for_run_step(ctx)` → `toolset.get_tools(ctx)` → MCP `tools/list`, with tool definitions re-collected every run step. The graph nodes carry the comment `# This will raise errors for any tool name conflicts`. Sources: [`tool_manager.py` v1.107.7](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/tool_manager.py), [`_agent_graph.py`](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/_agent_graph.py).
- **Schema mapping is a passthrough with client-side validation.** Each MCP tool becomes `ToolDefinition(name=..., description=mcp_tool.description, parameters_json_schema=mcp_tool.inputSchema, return_schema=mcp_tool.outputSchema, metadata={annotations, meta, output_schema})`; arguments are validated client-side against the JSON schema before the call ever hits the server. `isError` results become `ModelRetry(message)` (the server's error text goes back to the model as a retry hint); `structuredContent` is unwrapped and sent structured. Current `MCPToolset` adds: skipping tools whose MCP Apps `_meta.ui.visibility` omits `"model"`. Source: [`mcp.py` v1.107.7](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/mcp.py).
- **Name collisions: hard error, with a prescribed remedy.** `CombinedToolset.get_tools` raises `UserError` on conflict: "…defines a tool whose name conflicts with existing tool from {toolset.label}…", hinting `Set the tool_prefix attribute to avoid name conflicts.` (legacy) or `Wrap the toolset with .prefixed("...")` (`MCPToolset`). The docs prescribe prefixing each `MCPToolset` for multi-server setups. Source: [`toolsets/combined.py` v1.107.7](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/toolsets/combined.py), [MCP client docs](https://pydantic.dev/docs/ai/mcp/client/).

### Connection lifetime

- **Ref-counted, session-shared context managers — the most deliberate lifecycle design.** `MCPServer.__aenter__` increments a nesting counter; on first entry it spawns a dedicated `_session_runner` asyncio task that owns the transport's `AsyncExitStack` (comment: sessions are "Entered AND exited inside this single dedicated asyncio.Task, so the underlying anyio cancel scopes … always exited in the same task they were entered in"). `__aexit__` tears down only at zero. Source: [`mcp.py` v1.107.7](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/mcp.py).
- **Two usage modes:** implicit (opened and closed per run: "If you don't explicitly enter one of these context managers, the toolset will be opened and closed automatically as needed") or explicit long-lived (`async with agent:` — "This will start all `MCPServer…` registered as `toolsets` so they are ready to be used"). Current docs state directly: "An `MCPToolset` instance maintains one MCP session that's shared by all concurrent agent runs using it." Note the pooling is *session*-level: each enter cycle creates a fresh httpx connection pool — reuse comes from keeping the context open, not from a URL-keyed cache. Sources: [`agent/__init__.py` v1.107.7](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/agent/__init__.py), [MCP client docs](https://pydantic.dev/docs/ai/mcp/client/).
- **No sync API in the MCP layer** — everything is async (anyio/`ClientSession`); the docs show only `asyncio.run(...)` usage. Source: [MCP client docs](https://pydantic.dev/docs/ai/mcp/client/).

### Tool-list caching / refresh

- **Cached per connection with real `listChanged` support — the most complete refresh story.** `cache_tools: bool = True` (docs): "tools are fetched once and cached until either: The server sends a `notifications/tools/list_changed` notification; [`__aexit__`] is called (when the last context exits). Set to `False` for servers that change tools dynamically without sending notifications." The notification hook is real code: `ToolListChangedNotification` → `self._cached_tools = None` (v1) / `toolset._invalidate_tools_cache()` (main). Between notifications there is no TTL or polling. Source: [`mcp.py` v1.107.7](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/mcp.py), [main](https://github.com/pydantic/pydantic-ai/blob/main/pydantic_ai_slim/pydantic_ai/mcp.py).
- **Durable-execution caveat (unusual and important):** under Temporal/DBOS wrappers, "tool definitions are additionally cached at the wrapper level across activities/steps … This wrapper-level cache is not invalidated by `tools/list_changed` notifications. Set to `False` to disable all caching if tools may change during a workflow." Source: [`mcp.py` v1.107.7](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/mcp.py).

### Guardrails on untrusted output

- **No output guardrails implemented or documented.** Grepping `mcp.py` (v1.107.7 and main) for truncation/size limits returns nothing; tool results (structured content or mapped content parts, including server error text via `ModelRetry`) reach the model **verbatim and unbounded**. The only explicit security warnings in the docs concern **MCP config files** ("Treat configuration files as trusted input… never load them from untrusted sources") and elicitation approval controls — nothing about tool-description injection, poisoned output, or output caps. One notable undocumented attack surface: `include_instructions=True` (default `False`) injects the server-provided `instructions` string into the agent's instructions with no trust caveat in the docs. Source: [`mcp.py`](https://github.com/pydantic/pydantic-ai/blob/v1.107.7/pydantic_ai_slim/pydantic_ai/mcp.py), [`docs/mcp/client.md` (main)](https://github.com/pydantic/pydantic-ai/blob/main/docs/mcp/client.md).

## Observed conventions (and their implications)

1. **Nobody auto-registers tools as a side effect of `connect()`.** In OpenAI Agents SDK and Pydantic AI the model-visible tool list is recomputed from `tools/list` for each run/run-step; in LangChain and LlamaIndex the user pulls a converted tool list explicitly. Any AgentGraphStudio MCP integration can treat "list at run start, convert, expose" as the default contract, with Pydantic AI's `listChanged` invalidation and Claude's harness behavior as the two existing models for keeping that list fresh.
2. **MCP JSON Schemas flow through mostly unmodified.** Three of four Python frameworks consume the raw `inputSchema` dict (LangChain as `args_schema`, OpenAI with a small `properties` compat patch, Pydantic AI as `parameters_json_schema`); only LlamaIndex compiles a dynamic Pydantic model. If a server's schema contains advanced JSON-Schema features, strict-schema providers may reject it — OpenAI's opt-in `convert_schemas_to_strict=True` with silent fallback on failure is the only framework-level answer to that.
3. **Name collision policy splits into two camps — fail loudly or namespace proactively.** OpenAI Agents SDK and Pydantic AI raise hard errors and point at a prefix mechanism; LangChain (new) and Claude Agent SDK namespace unconditionally. LlamaIndex silently overwrites — an outlier worth avoiding. For a builder UI where servers are chosen by the user at runtime, a default prefix (`mcp__<server>__<tool>`-style, as Claude Agent SDK does) plus an error if the *prefixed* name still collides is the most ergonomic combination observed.
4. **Session sharing over pooling.** No framework implements a connection *pool* keyed by URL. Pooled/reused sessions are achieved by owning one long-lived session object: Pydantic AI's ref-counted context manager (shared across concurrent runs) is the most reusable pattern for a server-side orchestrator; LlamaIndex's fresh-session-per-tool-call is the pattern to avoid (a full HTTP + initialize handshake per tool call).
5. **`notifications/tools/list_changed` is honored by only two of five frameworks.** OpenAI Agents SDK explicitly does not handle it, and LangChain/LlamaIndex simply refetch on user demand. Pydantic AI's design (cache by default, invalidate on notification, `cache_tools=False` opt-out for silent-changing servers) plus Claude's "refresh fails → keep previous list" rule are the reference behaviors.
6. **Output guardrails are close to absent.** Only the Claude Agent SDK applies real output discipline (token caps, overflow-to-disk, transport size caps, middle-truncation of errors) despite the MCP spec's client-side instruction to "validate tool results before passing to LLM." Nothing in any framework *labels* output as untrusted/injected — mitigation everywhere is consent (approval to connect), permission gating on tool *invocation*, or opt-in user-supplied guardrail hooks, never per-result marking. A builder that streams MCP tool output into an agent-loop observation slot should not assume upstream sanitization.
